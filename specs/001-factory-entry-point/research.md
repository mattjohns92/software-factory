# Research: Bootstrap a Native-Workflow-Powered Factory Entry Point

**Date**: 2026-11-19

## Decision 1: Delegate to the Spec Kit workflow engine

**Decision**: The factory CLI will invoke `specify workflow run speckit --json --input "spec=<request>"`, inspect results with `specify workflow status <run-id> --json`, and resume with `specify workflow resume <run-id> --json`. The Spec Kit run ID and persisted step state are authoritative.

**Rationale**: The installed Specify CLI 1.0.6 exposes `workflow run`, `status`, and `resume`. The initial bundled Full SDD Cycle v1.0.1 lacked review verdict inputs. The adopted upstream workflow 1.0.2 is pinned to the `github/spec-kit` v1.4.2 tag and declares both verdict inputs; its `speckit_version: ">=0.15.1"` requirement is met by CLI 1.0.6. This is the native engine required by the spec, not Copilot CLI's separate dynamic-workflow command.

**Alternatives considered**: Calling `copilot workflow run` directly was rejected because it runs Copilot CLI extension workflows, not the registered Spec Kit workflow. A Python-owned phase engine, database, or direct integration API was rejected because it duplicates process state or bypasses the native dispatcher.

## Decision 2: Keep approvals in native gates and make rejection resumable

**Decision**: Use upstream `speckit` workflow 1.0.2, which declares the empty-by-default inputs `speckit_review_spec_verdict` and `speckit_review_plan_verdict`. Use a project-local overlay to replace only the two review gates, preserving each `verdict_input` binding and setting `on_reject: retry`. The factory's initial `run` command must never supply verdict values. A later explicit owner `resume` action supplies exactly one decision for the current gate through Spec Kit's `--input` option.

**Rationale**: Upstream PR [#5392](https://github.com/github/spec-kit/pull/5392), merged into Spec Kit and included in release v1.4.1, added empty-default verdict inputs to `speckit` workflow 1.0.2 while preserving the gates' upstream `on_reject: abort` behavior. The overlay changes only that rejection behavior to `retry`, which keeps a rejected gate paused on that step. The factory's initial dispatch omits verdict inputs; only a validated explicit resume supplies the matching decision.

**Alternatives considered**: Keeping `abort` would contradict the spec's rejected-decision resume scenario. Treating an abort as a new run would lose same-run identity. Automatically filling verdict inputs on initial run was rejected because it would bypass owner authority.

## Decision 3: Verify installed compatibility without pretending to verify authentication

**Decision**: Record Specify CLI 1.0.6, upstream `speckit` workflow 1.0.2 from the `github/spec-kit` v1.4.2 tag, and Copilot CLI 1.0.114 as the initial compatibility test tuple. `factory doctor` performs static preflight only: executable/version presence, `specify integration status --json`, and resolved `speckit` workflow plus its required verdict inputs. Do not run `copilot login`, prompt for secrets, or infer authentication from executable presence. Live dispatch is verified only by an explicitly owner-authorized disposable-repository run. If dispatch fails, inspect native state and report the actual error and run ID if available; if state is indeterminate, say so without inventing an ID or claiming no run exists.

**Rationale**: Local checks confirmed Specify CLI 1.0.6, Copilot CLI 1.0.114, active `copilot` integration, readable manifests, and no integration findings. `specify check` explicitly describes Copilot as IDE-based with no CLI check; Copilot CLI provides no supported non-model authentication/dispatch health command; `specify workflow run` has no dry-run mode. These are configuration facts, not proof of login or successful model dispatch. `copilot login` starts an OAuth/token flow and is not an appropriate automatic preflight action.

**Alternatives considered**: Checking only `Get-Command`/`shutil.which` was rejected as insufficient compatibility evidence. Automatically authenticating was rejected because it changes credentials and may expose sensitive input. Starting a real workflow as a smoke check during planning was rejected because it performs consequential work.

The installed Specify 1.0.6 / `speckit` 1.0.2 / Copilot 1.0.114 tuple is not yet certified. Certification requires the disposable-repository run, both owner gates, same-run resume, and security acceptance checks in [quickstart.md](quickstart.md). No native workflow has been dispatched.

## Decision 4: Use a deterministic phase-specific policy

**Decision**: Before dispatch, construct an allowlisted environment and set `SPECKIT_COPILOT_ALLOW_ALL_TOOLS=0`, legacy `SPECKIT_ALLOW_ALL_TOOLS=0`, and `COPILOT_ALLOW_ALL=false`. Omit inherited `SPECKIT_INTEGRATION_COPILOT_EXTRA_ARGS`, `SPECKIT_INTEGRATION_COPILOT_EXECUTABLE`, raw token variables, and unrelated credentials. Bind a versioned per-run policy to the approved-plan digest. Its schema contains `schema_version`, `approved_plan_digest`, canonical `repository_root`, `writable_paths`, `read_only_paths`, `denied_paths`, `allowed_tools`, and `allowed_commands`; each allowed command records its exact command text and working directory. Paths are explicit canonical absolute paths or descendants of explicitly approved roots; reject traversal, UNC/device paths, and symlink/reparse escapes. On Windows, compare canonical paths case-insensitively. Any missing, malformed, stale, or mismatched policy blocks dispatch.

Use only fixed, version-verified Copilot arguments. The pinned tool profile is limited to the required documented CLI tools (`view`, `glob`, `grep`, `create`, `edit`, `apply_patch`, and `powershell`); no web tools or subagent tool are available. Disable built-in MCPs, enumerate and disable every configured non-factory MCP, and load no plugins. Inventory machine policy, user, repository file, inline settings, and plugin hook sources. The CLI has no supported “load only this hook” option: `disableAllHooks` disables the factory hook too, while administrator policy hooks cannot be disabled. Use a dedicated factory user configuration profile for the factory hook; reject unreviewed repository/inline hook sources, active plugins, or unenumerable policy sources. The factory `preToolUse` hook denies malformed/unknown events and requests outside the policy, but is supplemental only. The official reference documents command-hook timeouts as fail-open to normal permission handling, so the hook cannot be the sole security boundary. The Windows OS sandbox and restrictive tool permissions must independently deny prohibited paths/actions. A disposable probe must establish this even with the hook absent or timed out. Hosted inference is consented separately; URL denials are not treated as a network firewall.

**Policy lifecycle**: The native run starts before the plan has been approved. Its `phase=planning` policy therefore has a null `approved_plan_digest`, allows writes only to designated Spec Kit planning artifacts for the current feature, and prohibits application implementation paths. After explicit plan approval, replace it with `phase=implementation`, require the exact non-null approved-plan digest, and grant only the approved application paths and local checks. A policy transition failure blocks the protected phase.

Digest binding applies only to the implementation-phase policy. The planning-phase policy remains unbound because there is no approved plan at that stage.

**Hook source**: Keep exactly one reviewed repository hook at `.github/hooks/factory-policy.json`; its command invokes `scripts/factory_pre_tool_use.ps1`. The dedicated `COPILOT_HOME` isolates user-level settings and hooks, but does not suppress repository hooks or administrator policy hooks. Inventory those separately, and block on any unreviewed repository/inline/plugin hook or unknown policy hook.

**Rationale**: The installed Spec Kit Copilot dispatcher adds `--yolo` unless `SPECKIT_COPILOT_ALLOW_ALL_TOOLS` is exactly `0`, so that environment setting and the inherited extra-argument override must be controlled. Copilot CLI 1.0.114 accepts `--sandbox`, `--available-tools`, `--deny-tool`, `--disable-builtin-mcps`, and `--disable-mcp-server`. Official documentation says built-in MCP disabling does not disable custom MCPs, hooks are combined across policy/user/repository/plugin sources, policy hooks cannot be disabled, and command `preToolUse` timeouts fail open. CLI documentation describes Windows sandbox filesystem/process containment, but configuration or a recognized flag is not evidence that the effective runtime blocks the required actions. The probe is the only evidence for the tested CLI/runtime/policy fingerprint.

**Alternatives considered**: Accepting `--yolo`, broad shell/network access, inherited MCPs, plugins, or unreviewed hooks was rejected. Treating `preToolUse` as a complete boundary, assuming an unsupported single-hook switch exists, or treating `--sandbox` acceptance or URL denial as proof of enforcement was rejected. If the pinned CLI cannot establish independent runtime restrictions, do not dispatch; do not silently weaken the policy.

## Decision 5: Keep the application dependency-light

**Decision**: Use Python 3.11+, `argparse`, `subprocess` with argument arrays and `shell=False`, and `unittest`. Use `uv` for environment and lock management, commit `uv.lock` for reproducible setup, and use a build-only backend for the installable console command. No runtime framework, database, or YAML parser is needed for the wrapper.

**Rationale**: The repository has no application source, package metadata, or tests. The wrapper's responsibilities are CLI parsing, preflight, safe process invocation, and report formatting. Spec Kit remains responsible for workflow YAML parsing and state.

**Alternatives considered**: Click/Typer and pytest were not selected for the initial slice because their richer APIs do not justify adding runtime/test dependencies yet. Parsing workflow YAML in Python was rejected because it would duplicate Spec Kit behavior.

## Decision 6: Separate static readiness from live compatibility

**Decision**: `factory doctor` reports only static local prerequisites and must label authentication, dispatch, and effective sandbox behavior unverified. Only a separate owner-authorized disposable-repository workflow run can certify the observed version/environment tuple. A failed or indeterminate dispatch is reported with actual state evidence; it never becomes a simulated success or a fabricated run result.

**Rationale**: No supported non-model, non-workflow command in the installed CLIs proves both Copilot authentication and Specify-to-Copilot dispatch. `specify integration status` validates registration and managed-file integrity; `specify check` does not test the Copilot CLI. The native `specify workflow run` command has no dry-run option and may create persisted state before command dispatch fails.

**Alternatives considered**: Claiming successful live compatibility from executable presence or integration registration was rejected. Automatically logging in or making an unapproved canary request was rejected. Starting a duplicate native run to recover an uncertain dispatch was rejected.

## Decision 7: Obtain per-run authorization before hosted inference

**Decision**: Before invoking the native workflow, identify the configured inference service and disclose that the feature request, relevant repository content, and selected tool output may be transmitted for inference; disclose that use may consume subscription quota or credits. Obtain an explicit yes/no decision for each run. Interactive mode prompts after disclosure. Non-interactive mode requires an explicit `--authorize-hosted-agent` flag whose documented meaning includes the same disclosure. A refusal or unidentifiable provider blocks before any agent invocation; consent is not persisted or treated as approval of the specification/plan or of external actions.

**Rationale**: The constitution separates permission to edit files from permission for network access, external integrations, and credentials. Copilot CLI supports hosted inference and can also be configured with other providers, so the actual provider must be identified rather than assumed. The user must authorize the data transfer before the request or repository context is sent.

**Alternatives considered**: Treating the feature request itself as consent, persisting a global consent flag, or conflating hosted-inference consent with native spec/plan approval was rejected.

## Decision 8: Require independent sandbox enforcement for scope

**Decision**: Compile the approved plan's explicit writable/read-only/denied paths, pinned tool names, and exact permitted local-check commands into the plan-digest-bound policy. The factory hook checks pre-tool requests and denies unknown or malformed events. The disposable acceptance probe must also demonstrate an out-of-scope write is denied by the effective Windows sandbox when the hook is absent or deliberately times out, and that no diff is produced. Verify allowed local checks still work. If the CLI/runtime cannot independently enforce the required path and tool boundaries, block native workflow dispatch.

**Rationale**: Copilot CLI's pre-tool command hook is fail-closed for ordinary nonzero failures but documented as fail-open on timeout; an ensuing normal permission flow is not equivalent to a deterministic denial. CLI command-level path checks are not a substitute for OS containment. The hook remains useful for auditable exact policy decisions, but the operating-system sandbox and restrictive tool policy must remain effective without it.

**Alternatives considered**: Relying on model instructions, the hook alone, checking only the final Git diff, or assuming that `--sandbox` alone enforces the intended path scope was rejected.

## Decision 10: Resolve required-check conflicts conservatively

**Decision**: The required-check set is the union of checks listed by the approved plan, checks explicitly required by checked-in CI configuration or repository contributor/instruction documentation, and branch-protection checks supplied by the owner. The approved plan cannot waive a repository-mandated check. If a check cannot be identified or the sources conflict in a way that cannot be satisfied together, block a verified outcome and ask the owner to resolve it. If remote-only branch-protection requirements are not supplied and cannot be inspected through an already-authorized integration, the check set is incomplete and cannot be reported verified. Changing repository requirements needs separate explicit authorization.

**Rationale**: The feature specification names both sources but previously left precedence and source discovery implicit. Union preserves both authorities without silently weakening repository policy; inaccessible remote-only rules remain unknown rather than being inferred. Impossible or ambiguous combinations require owner resolution rather than an agent interpretation.

**Alternatives considered**: Letting the plan override repository requirements, taking only the intersection, or silently choosing one source was rejected.

## Decision 9: Record provenance and an explicit completion review

**Decision**: Maintain the adopted/executed component inventory in this research artifact and update it when a component changes. Each entry records origin, pinned version/reference, license, modifications, and purpose. Before a run is reported complete, compare actual changes with approved requirements and scope, record actionable findings, and label the review independent or self-review.

**Rationale**: The constitution requires reviewed third-party provenance and an evidence-based review. The inventory also distinguishes tools invoked locally from software redistributed by the factory. Copilot CLI is not bundled or modified; its separate license and service terms remain applicable.

**Alternatives considered**: Inferring licenses from package names or treating a passing test command as a requirements review was rejected.
